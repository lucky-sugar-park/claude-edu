# 예제: Claude Code에게 일을 시키는 프롬프트 모범 사례

> 관련 모듈: 5 (전 모듈에 공통 적용)
> 예제 프로젝트: [EduHub](./00-sample-project.md)

---

## 1. 기본 원칙: "유능한 신입 동료에게 일을 맡기듯"

Claude는 코딩 능력은 뛰어나지만 **우리 팀의 사정은 모릅니다**. 일을 잘 맡기는 방법은 사람에게 맡길 때와 같습니다.

| 원칙 | 설명 |
|---|---|
| **목표를 말한다** | 무엇을 만들지뿐 아니라 **왜** 필요한지 |
| **맥락을 준다** | 관련 파일, 참고할 기존 코드, 제약 조건 |
| **완료 기준을 정한다** | 무엇이 되면 끝인지, 어떻게 확인하는지 |
| **검증 수단을 준다** | 테스트 명령, 확인할 화면, 기대 출력 |
| **큰 일은 나눈다** | 탐색 → 계획 → 구현 → 검증 |

## 2. 프롬프트 구성 템플릿

```text
[목표] 무엇을, 왜
[맥락] 관련 파일·기존 코드·참고 예제
[요구사항/규칙] 반드시 지켜야 할 것, 하지 말아야 할 것
[완료 기준] 무엇으로 확인하는가
[진행 방식] 계획 먼저 / 바로 구현 / 질문 먼저
```

모든 항목을 매번 쓸 필요는 없습니다. 작업이 클수록 더 많이 채웁니다. 매번 반복되는 규칙은 CLAUDE.md로 옮깁니다.

## 3. 모범 사례 12가지

### ① 구체적으로 지시한다

| ❌ | ✅ |
|---|---|
| "수강 신청 테스트 추가해줘" | "`EnrollmentService.enroll()`에 테스트를 추가해줘. 정원이 찬 경우, 이미 신청한 경우, 취소 후 재신청 경우를 다뤄줘. 목(mock)은 쓰지 말고 `@DataJpaTest`로 작성해줘" |
| "화면 예쁘게 해줘" | "과정 목록 카드에 카테고리 Chip, 남은 자리 수, 마감 임박(3석 이하) 시 빨간 Badge를 추가해줘. MUI 사내 테마 색상만 사용해줘" |

### ② 위치를 알려준다

```text
backend/.../enrollment/EnrollmentService.java의 cancel() 메서드를 수정해줘.
```

정확한 위치를 주면 탐색 시간과 토큰이 줄고, 엉뚱한 곳을 수정할 가능성도 줄어듭니다. IDE에서는 파일을 열거나 코드를 선택한 상태로 지시하면 됩니다.

### ③ 참고할 기존 코드를 지정한다

```text
CourseController의 목록 조회 API와 같은 방식(페이징, 응답 DTO, OpenAPI 어노테이션)으로 EnrollmentController에 내 신청 목록 API를 추가해줘.
```

> 💡 "우리 방식대로"라는 말보다 **"이 파일처럼"**이 훨씬 정확합니다.

### ④ 검증 방법을 준다 (가장 중요)

```text
완료 후 ./gradlew test --tests "*Enrollment*" -q를 실행해서 통과를 확인해줘.
실패하면 원인을 고치고 다시 실행해줘. 테스트 코드는 수정하지 마.
```

에이전트는 **스스로 확인할 수단이 있을 때** 가장 잘 일합니다. 테스트, 빌드, 린트, 스크린샷, 기대 출력 등 무엇이든 좋습니다.

### ⑤ 큰 작업은 계획부터

```text
수강 대기자 자동 승격 기능을 추가하려고 해.
먼저 관련 코드를 읽고 구현 계획을 세워줘. 아직 코드는 수정하지 마.
```

→ 계획을 검토하고 수정 의견을 준 뒤 "좋아, 진행해줘". Plan 모드를 쓰면 같은 흐름을 더 안전하게 진행할 수 있습니다.

### ⑥ 탐색 → 계획 → 구현 → 검증을 분리한다

```text
1단계: shell과 remote의 MUI 버전과 테마 사용 방식을 조사해서 정리해줘.
(결과 확인 후)
2단계: 조사 결과를 바탕으로 테마가 깨지는 원인과 해결 방안 2가지를 비교해줘.
(선택 후)
3단계: 방안 A로 수정하고, 모든 remote를 띄워 확인하는 방법을 알려줘.
```

### ⑦ 에러는 그대로 붙여넣는다

```text
과정 상세 API를 호출하면 아래 에러가 나. 원인을 찾아서 고쳐줘.

org.hibernate.LazyInitializationException: could not initialize proxy
  [com.example.eduhub.course.Course#3] - no Session
    at ...CourseDetailResponse.from(CourseDetailResponse.java:21)
    ...
```

요약하지 말고 **원문 그대로** 주는 것이 가장 좋은 맥락입니다. 화면 문제는 스크린샷을 붙여넣습니다.

### ⑧ 하지 말아야 할 것을 명시한다

```text
- 기존 Flyway 마이그레이션 파일은 수정하지 마
- public API의 응답 형식은 바꾸지 마 (프론트가 사용 중)
- 새 라이브러리는 추가하지 말고 기존 의존성으로 해결해줘
```

### ⑨ 이유를 함께 말한다

| ❌ | ✅ |
|---|---|
| "Enrollment에 락 걸어줘" | "동시에 신청하면 정원을 초과하는 문제가 있어. 신청이 몰리는 인기 과정에서 실제로 발생했어. 정원 초과가 절대 없도록 고쳐줘" |

이유를 알면 Claude가 **더 나은 해결책**(락 대신 다른 방법 등)을 제안할 수 있습니다.

### ⑩ 모르면 묻게 한다

```text
요구사항이 불명확하거나 선택지가 여러 개면 추측하지 말고 먼저 질문해줘.
```

### ⑪ 방향이 틀리면 빨리 멈춘다

- 진행 중 잘못된 방향이 보이면 **즉시 중단**(Esc)하고 지시를 고친다
- 잘못된 수정은 체크포인트·되돌리기(rewind)로 되돌린다
- 같은 실수를 두 번 이상 하면 대화를 이어가지 말고 `/clear` 후 더 나은 지시로 새로 시작한다

### ⑫ 반복되는 지시는 자산으로 만든다

| 반복되는 것 | 옮길 곳 |
|---|---|
| 매번 말하는 규칙 | CLAUDE.md |
| 매번 쓰는 절차 | 스킬, 슬래시 커맨드 |
| 매번 맡기는 역할 | 서브에이전트 |
| 매번 확인하는 검사 | 훅 |

## 4. 작업 유형별 프롬프트 예시 (EduHub)

### 4-1. 코드 이해

```text
수강 신청 흐름을 enrollment-mfe의 "신청" 버튼부터 DB 저장까지 따라가며 설명해줘.
관련 파일 경로와 핵심 메서드를 순서대로 정리하고, 트랜잭션 경계가 어디인지 표시해줘.
```

### 4-2. 기능 구현

```text
[목표] 마이페이지에 "수료 현황" 화면을 추가해줘. 임직원이 올해 수료한 과정과 총 교육 시간을 볼 수 있어야 해.
[맥락] 수료 정보는 enrollment.status = COMPLETED. 화면은 enrollment-mfe의 MyPage에 탭으로 추가.
       API는 EnrollmentController의 기존 목록 API 방식을 따라줘.
[규칙] 집계는 DB에서(JPQL 또는 DTO 프로젝션). 엔티티 직접 반환 금지. MUI Tabs 사용.
[완료 기준] 백엔드 테스트 통과, npm test 통과, Swagger에 새 API 표시.
[진행] 먼저 계획을 보여줘.
```

### 4-3. 버그 수정

```text
[현상] 대기자가 있는 회차에서 신청을 취소해도 대기자가 승격되지 않아.
[재현] 정원 1명인 회차에 A 신청, B 대기 → A 취소 → B 상태가 WAITING 그대로.
[기대] B가 APPLIED로 바뀌어야 함.
먼저 이 현상을 재현하는 실패 테스트를 작성하고, 그다음 원인을 찾아 고쳐줘.
```

### 4-4. 리팩터링

```text
EnrollmentService가 400줄이 넘었어. 동작은 바꾸지 말고 신청/취소/대기 처리로 책임을 나눠줘.
리팩터링 전에 기존 테스트가 모두 통과하는지 먼저 확인하고, 리팩터링 후에도 같은 테스트가 통과해야 해.
public 메서드 시그니처는 유지해줘.
```

### 4-5. 코드 리뷰

```text
현재 브랜치의 변경 사항(main 대비)을 리뷰해줘.
JPA 성능, 트랜잭션, API 하위 호환성, MFE shared 의존성 관점으로 보고,
심각도(높음/중간/낮음)로 분류해서 파일과 줄 번호를 알려줘. 코드는 수정하지 마.
```

### 4-6. 서브에이전트 활용

```text
code-explorer 에이전트로 frontend 전체에서 Axios를 직접 생성하거나 import하는 곳을 찾아줘.
결과를 받으면 api-client 사용으로 바꾸는 계획을 세워줘.
```

## 5. 안티 패턴

| 안티 패턴 | 문제 | 개선 |
|---|---|---|
| "알아서 잘 해줘" | 목표와 기준이 없어 결과가 매번 다르다 | 목표, 완료 기준 명시 |
| 한 번에 너무 많은 일 | 중간에 방향이 틀어져도 알기 어렵다 | 단계별로 나누고 중간 확인 |
| 대화 하나에서 여러 주제 | 이전 맥락이 섞여 품질 저하, 토큰 낭비 | 주제가 바뀌면 `/clear` |
| 결과를 확인하지 않고 커밋 | 그럴듯하지만 틀린 코드가 들어간다 | 테스트 실행, diff 직접 확인 |
| 같은 지적 반복 | 대화가 길어질수록 수정이 어려워진다 | 지시를 다시 써서 새로 시작, 규칙은 CLAUDE.md로 |
| 테스트를 고쳐서 통과시키게 둠 | 버그가 숨는다 | "테스트 코드는 수정하지 마" 명시 |

## 6. 실습: 프롬프트 개선 워크숍

   - "로그인 안 되는 거 고쳐줘"
   - "과정 검색 기능 만들어줘"
   - "성능 좀 개선해줘"
2. 원래 지시와 개선한 지시로 각각 실행하고 결과 비교 (품질, 소요 시간, 토큰 사용량)
3. 팀에서 가장 효과가 좋았던 프롬프트를 모아 팀 "프롬프트 모음집" 문서로 정리
4. 반복되는 부분은 CLAUDE.md, 스킬로 옮길 후보를 선정
