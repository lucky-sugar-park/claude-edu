# 개념 정리와 토론: CLAUDE.md로 쓸까, 스킬로 만들까, 에이전트로 만들까?

> 관련 모듈: 2 (개념 소개), 12 (확장 기능을 모두 배운 뒤 다시 토론)
> 예제 프로젝트: [EduHub](./00-sample-project.md)

초보자가 가장 헷갈려하는 부분입니다. **"누가 호출하는가"**를 기준으로 구분하면 쉽게 정리됩니다.

---

## 1. 꼭 짚어줄 개념 비교표

| 기능 | 누가 호출하나 | 주 용도 |
|---|---|---|
| **CLAUDE.md** | 항상 자동 로드 | 프로젝트의 기본 맥락과 규칙 |
| **슬래시 커맨드** | 사용자가 직접 | 자주 쓰는 프롬프트 저장 |
| **스킬(Skill)** | Claude가 상황을 보고 판단 | 특정 작업의 전문 지식·절차 묶음 |
| **서브에이전트(Subagent)** | Claude 또는 사용자가 위임 | 독립된 컨텍스트에서 역할별 작업 |
| **훅(Hooks)** | 이벤트 발생 시 자동 | 반드시 실행돼야 하는 규칙 강제 |

함께 알아 두면 좋은 두 가지:

| 기능 | 누가 호출하나 | 주 용도 |
|---|---|---|
| **MCP / 커넥터** | Claude가 필요할 때 도구로 호출 | 외부 시스템·데이터 연결 |
| **플러그인** | (호출 대상이 아님) 설치하는 묶음 | 위 기능들을 묶어 배포 |

> 💡 최근 버전에서는 스킬도 `/스킬이름`으로 직접 부를 수 있어 슬래시 커맨드와 경계가 가까워졌습니다. 구분의 핵심은 **"Claude가 스스로 꺼내 쓸 수 있는가(스킬)"** vs **"사람이 부를 때만 쓰는가(커맨드)"**입니다.

### 한 문장 비유

- **CLAUDE.md** = 신입에게 주는 **온보딩 문서** (항상 책상 위에 있음)
- **슬래시 커맨드** = 자주 쓰는 **요청서 양식** (내가 꺼내서 씀)
- **스킬** = 책장에 꽂힌 **업무 매뉴얼** (필요할 때 직원이 알아서 꺼내 봄)
- **서브에이전트** = 일을 맡길 수 있는 **전문 팀원** (자기 책상에서 따로 일하고 결과만 보고)
- **훅** = 출입구의 **자동 검문소** (누구든 지나가면 무조건 검사)

## 2. 판단 흐름

```
이 내용이 …
│
├─ 모든 작업에서 항상 알아야 하는 짧은 규칙인가? ─────────── 예 → CLAUDE.md
│
├─ 어기면 안 되고, 기계적으로 검사할 수 있는가? ─────────── 예 → 훅 (+ CLAUDE.md에 한 줄 안내)
│
├─ 특정 작업에서만 필요한 절차·지식인가?
│     ├─ Claude가 상황에 맞게 알아서 쓰면 좋겠다 ─────────── → 스킬
│     └─ 내가 원할 때만 실행하면 된다 ─────────────────── → 슬래시 커맨드
│
├─ 별도 컨텍스트, 제한된 권한, 다른 모델이 필요한 "역할"인가? ── 예 → 서브에이전트
│
└─ 외부 시스템의 데이터나 기능이 필요한가? ──────────────── 예 → MCP
```

### 자주 하는 실수

| 실수 | 문제 | 바로잡기 |
|---|---|---|
| 모든 절차를 CLAUDE.md에 씀 | 매 턴 토큰 낭비, 중요한 규칙이 묻힘 | 긴 절차는 스킬로 |
| "절대 하지 마"를 CLAUDE.md에만 씀 | 강제력이 없어 가끔 어김 | 훅이나 권한 설정으로 강제 |
| 절차를 알려주려고 에이전트를 만듦 | 맥락을 모르는 별도 에이전트가 일해 결과가 어긋남 | 절차는 스킬, 에이전트는 "역할"에 |
| 모든 걸 훅으로 처리 | 판단이 필요한 규칙은 스크립트로 검사 불가, 작업이 느려짐 | 기계적 검사만 훅으로 |

## 3. 토론 실습: 같은 요구사항, 다섯 가지 구현

**요구사항:** "EduHub에 새 API를 추가할 때 OpenAPI 문서(`@Operation`, `@ApiResponse`)가 빠지지 않게 하고 싶다."

### 방식 A. CLAUDE.md

```markdown
## API / OpenAPI
- 모든 컨트롤러 메서드에 `@Operation(summary=...)`과 실패 응답 `@ApiResponse`를 단다
```

### 방식 B. 슬래시 커맨드

```markdown
<!-- .claude/commands/check-openapi.md -->
backend의 변경된 컨트롤러를 확인해서 @Operation, @ApiResponse가 빠진 메서드를 찾고 보완해줘.
```

→ 사용자가 작업 후 `/check-openapi` 실행

### 방식 C. 스킬

```markdown
---
name: openapi-docs
description: Spring 컨트롤러에 API를 추가·수정할 때 사용한다. OpenAPI 어노테이션 작성 규칙, 에러 응답 문서화 예시, 누락 검사 스크립트를 제공한다.
---
(어노테이션 규칙, 예시 코드, scripts/check-openapi.sh 사용법)
```

### 방식 D. 서브에이전트

```markdown
---
name: api-doc-reviewer
description: API 변경 후 OpenAPI 문서 품질을 검토한다. 누락된 어노테이션, 부정확한 설명, 문서화되지 않은 에러 응답을 보고한다.
tools: Read, Grep, Glob
---
```

### 방식 E. 훅

```json
{ "hooks": { "PostToolUse": [ { "matcher": "Edit|Write",
  "hooks": [ { "type": "command", "command": "bash .claude/hooks/check-openapi.sh" } ] } ] } }
```

→ 컨트롤러 파일이 수정될 때마다 검사 스크립트 실행, 누락 시 Claude에게 알림

### 비교표 (토론 후 함께 채우기)

| 기준 | A. CLAUDE.md | B. 커맨드 | C. 스킬 | D. 서브에이전트 | E. 훅 |
|---|---|---|---|---|---|
| 확실히 지켜지는가 | 대부분 | 실행할 때만 | 대부분 | 검토할 때만 | **항상** |
| 문서의 **품질**(설명이 정확한가)까지 보는가 | 일부 | 예 | 예 | **예 (깊게)** | 아니오 (존재 여부만) |
| 토큰 비용 | 매 턴 조금 | 실행 시 | 필요할 때만 | 별도 컨텍스트 | 거의 없음 |
| 만드는 수고 | 매우 적음 | 적음 | 보통 | 보통 | 스크립트 필요 |
| 사람이 기억해야 하나 | 아니오 | **예** | 아니오 | 경우에 따라 | 아니오 |

### 모범 답안 예시: 조합하기

> **A + C + E** 조합을 추천합니다.
> - **CLAUDE.md**에 한 줄 규칙 → Claude가 처음부터 의식함
> - **스킬**로 상세 예시 제공 → 품질 높은 문서 작성
> - **훅**으로 누락 검사 → 빠뜨려도 바로 잡힘
> - (선택) 큰 기능이면 **서브에이전트**로 문서 품질까지 검토
>
> 정답은 하나가 아닙니다. 팀 규모, 규칙의 중요도, 유지 비용에 따라 달라집니다.

### 토론 질문

1. 방식 A만 쓴다면 어떤 상황에서 규칙이 지켜지지 않을까?
2. 방식 E(훅)만으로 충분하지 않은 이유는? (힌트: "존재"와 "품질")
3. 방식 B(커맨드)가 더 나은 상황은? (힌트: 가끔만 필요한 무거운 검사)
4. 우리 팀이라면 어떤 조합을 고르겠는가? 그 이유는?
