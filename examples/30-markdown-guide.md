# 마크다운(Markdown) 작성 가이드: 개발자가 자주 쓰는 문법 중심

> Claude Code와 일할 때 쓰는 문서(CLAUDE.md, 스킬의 SKILL.md, 요구사항, README, PR 본문, 이슈)는 대부분 마크다운입니다. 이 문서는 **실무에서 자주 쓰는 문법**을 예제와 함께 정리합니다.
> 기준: GitHub에서 쓰는 마크다운(GitHub Flavored Markdown, GFM). 다른 도구에서는 일부 문법(체크리스트, 알림 상자, Mermaid 등)이 다르게 보일 수 있습니다.
> 빠르게 핵심만 보려면 [2회차 자료의 마크다운 기본](../sessions/session-02-hands-on-kickoff.md#잠깐-마크다운-기본-5분)을 먼저 봅니다.

## 1. 왜 마크다운인가

| 이유 | 설명 |
|---|---|
| **텍스트 파일이다** | Git으로 변경 이력을 관리하고 diff로 리뷰할 수 있다 |
| **읽기 쉽다** | 렌더링하지 않은 원문 상태로도 구조가 보인다 |
| **어디서나 보인다** | GitHub, IDE, 위키, 사내 문서 도구 대부분이 지원한다 |
| **AI가 잘 읽는다** | 제목·목록·표로 구조를 나누면 Claude가 지시와 규칙을 정확히 구분한다. Claude의 답변도 마크다운으로 나온다 |

**Claude Code에서 마크다운을 쓰는 곳**

| 파일 | 용도 |
|---|---|
| `CLAUDE.md` | 매 세션 읽히는 프로젝트 지침 |
| `.claude/skills/*/SKILL.md` | 스킬 정의 (맨 위 YAML 머리말 + 마크다운 본문) |
| `.claude/agents/*.md` | 서브에이전트 정의 |
| `.claude/commands/*.md` | 사용자 정의 슬래시 커맨드 |
| `docs/*.md` | 요구사항, 설계, 런북 |
| `README.md`, PR·이슈 본문 | 팀과 공유하는 설명 |

## 2. 제목

`#`의 개수가 제목의 단계입니다. `#` 뒤에는 **반드시 한 칸 띄웁니다.**

```markdown
# 문서 제목 (한 문서에 하나)
## 큰 절
### 작은 절
#### 더 작은 절 (보통 여기까지만 쓴다)
```

**요령**
- `#`은 문서 맨 위에 **한 번만** 씁니다
- 단계를 건너뛰지 않습니다 (`##` 다음에 바로 `####` ✕)
- 제목은 GitHub에서 **자동으로 링크 주소(앵커)**가 됩니다 → [9장](#9-링크와-이미지)의 문서 내부 링크

## 3. 문단과 줄바꿈

```markdown
첫 번째 문단입니다.
이 줄은 같은 문단으로 이어져 보입니다.

빈 줄을 하나 넣으면 새 문단이 됩니다.

줄 끝에 백슬래시를 붙이면\
문단을 나누지 않고 줄만 바꿉니다.
```

| 하고 싶은 것 | 방법 |
|---|---|
| 새 문단 | 빈 줄 하나 |
| 문단 안에서 줄바꿈 | 줄 끝에 `\` 또는 공백 두 칸 (공백은 눈에 안 보여 실수가 잦으므로 `\` 권장) |
| 표 칸 안에서 줄바꿈 | `<br>` |

## 4. 강조

| 원문 | 결과 | 용도 |
|---|---|---|
| `**굵게**` | **굵게** | 핵심 단어 (가장 많이 씀) |
| `*기울임*` | *기울임* | 용어, 약한 강조 |
| `~~취소선~~` | ~~취소선~~ | 폐기된 내용 |
| `` `코드` `` | `코드` | 파일명, 명령, 클래스명, 설정 키 |

> 💡 강조 기호 바로 안쪽이 문장부호이고 바깥이 글자이면 강조가 적용되지 않습니다. 예: `**"정원"**을` ✕ → `"**정원**"을` 또는 `**"정원"** 을`. 결과가 이상하면 미리보기로 확인합니다.

## 5. 글머리 목록과 번호 목록

### 5-1. 글머리 목록

`-`, `*`, `+` 모두 되지만 **한 문서에서는 `-` 하나로 통일**합니다.

```markdown
- 백엔드: Spring Boot 3
- 프론트엔드: React 18
  - shell
  - course-mfe
- DB: PostgreSQL
```

결과:

- 백엔드: Spring Boot 3
- 프론트엔드: React 18
  - shell
  - course-mfe
- DB: PostgreSQL

**하위 목록**은 상위 항목의 글자 시작 위치에 맞춰 **2칸**(번호 목록 안에서는 3칸) 들여씁니다.

### 5-2. 번호 목록

순서가 중요할 때(절차, 우선순위) 씁니다.

```markdown
1. 저장소를 클론한다
2. 브랜치를 만든다
3. 구현하고 테스트한다
```

> 💡 숫자를 모두 `1.`로 써도 자동으로 1, 2, 3이 매겨집니다. 중간에 항목을 넣어도 번호를 고칠 필요가 없어 편합니다.

### 5-3. 목록 안에 문단·코드 넣기

목록 항목 아래 내용은 항목 글자 위치만큼 들여씁니다.

````markdown
1. 테스트를 실행한다

   ```bash
   ./gradlew test
   ```

2. 결과를 확인한다
````

### 5-4. 글머리 vs 번호 vs 표: 언제 무엇을

| 내용 | 추천 |
|---|---|
| 순서 없는 나열 (규칙, 특징) | 글머리 목록 |
| 순서가 있는 절차, 우선순위 | 번호 목록 |
| 같은 속성을 여러 항목에 대해 비교 | **표** |
| 할 일, 확인 항목 | 체크리스트 |

## 6. 체크리스트

```markdown
- [x] 저장소 생성
- [ ] 백엔드 뼈대
- [ ] CLAUDE.md 작성
```

결과:

- [x] 저장소 생성
- [ ] 백엔드 뼈대
- [ ] CLAUDE.md 작성

- `- [ ]` 사이의 공백에 주의합니다 (`-[ ]`, `- []` ✕)
- GitHub의 이슈·PR 본문에서는 체크박스를 **클릭해서** 체크할 수 있습니다
- PR 템플릿의 "확인 항목", 과제 목록에 자주 씁니다

## 7. 표

### 7-1. 기본 형태

```markdown
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 과정 목록 조회 | 필수 |
| FR-02 | 과정 상세 조회 | 필수 |
```

결과:

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 과정 목록 조회 | 필수 |
| FR-02 | 과정 상세 조회 | 필수 |

- 첫 줄은 **머리글**, 둘째 줄의 `|---|`은 머리글과 내용을 나누는 **구분줄**(필수)
- 줄 맨 앞과 끝의 `|`는 생략할 수 있지만 **붙이는 편이 읽기 쉽습니다**
- 원문에서 칸 너비를 맞출 필요는 없습니다 (맞추면 보기 좋지만 수정할 때 번거로움)
- 표 **위아래에 빈 줄**을 둡니다. 문단에 붙이면 표로 인식되지 않을 수 있습니다

### 7-2. 정렬

구분줄에 `:`를 붙여 칸 정렬을 정합니다.

```markdown
| 왼쪽 | 가운데 | 오른쪽 |
|:---|:---:|---:|
| 이름 | 상태 | 1,200 |
```

| 왼쪽 | 가운데 | 오른쪽 |
|:---|:---:|---:|
| 이름 | 상태 | 1,200 |

> 숫자(금액, 건수)는 오른쪽 정렬이 읽기 쉽습니다.

### 7-3. 표 안에서 자주 막히는 것

| 하고 싶은 것 | 방법 | 예 |
|---|---|---|
| 칸 안에서 줄바꿈 | `<br>` | `첫 줄<br>둘째 줄` |
| 칸 안에 `\|` 문자 쓰기 | `\|`로 이스케이프 | `a \| b` |
| 칸 안에 코드 | 백틱 | `` `./gradlew test` `` |
| 칸 안에 목록 | 지원하지 않음 → `<br>`과 `•` 또는 `①②③`로 대신 | `① 조회<br>② 신청` |
| 빈 칸 | 비워 두거나 `—` | |
| 칸 병합 | **지원하지 않음** → 표를 나누거나 HTML 표를 쓴다 | |

> 💡 표가 너무 넓어지면(칸 6개 이상, 칸마다 긴 문장) 읽기 어렵습니다. 그럴 때는 표를 나누거나, 항목별 소제목 + 글머리 목록으로 바꿉니다.

## 8. 코드

### 8-1. 인라인 코드

문장 안의 파일명, 명령, 클래스명은 백틱 하나로 감쌉니다: `` `EnrollmentService` `` → `EnrollmentService`

### 8-2. 코드 블록

백틱 세 개로 감싸고, 여는 백틱 뒤에 **언어 이름**을 적으면 문법 강조가 됩니다.

````markdown
```java
@GetMapping("/api/health")
public String health() {
    return "ok";
}
```
````

| 자주 쓰는 언어 이름 | 용도 |
|---|---|
| `java`, `kotlin` | 백엔드 코드, `build.gradle.kts` |
| `ts`, `tsx`, `js` | 프론트엔드 |
| `bash`, `powershell` | 터미널 명령 |
| `json`, `yaml` | `settings.json`, `application.yml` |
| `sql` | 쿼리, 마이그레이션 |
| `diff` | 변경 전후 (`+`, `-` 줄 색 표시) |
| `text` | 강조 없이 그대로 (프롬프트 예시, 로그) |
| `mermaid` | 다이어그램 ([12장](#12-다이어그램-mermaid)) |

### 8-3. 코드 블록 안에 코드 블록 넣기

바깥 블록의 백틱을 **네 개**로 하거나 `~~~`를 씁니다. (이 문서의 예제들이 그렇게 작성되어 있습니다)

`````markdown
./gradlew test
```
`````

## 9. 링크와 이미지

### 9-1. 링크

```markdown
[Claude Code 문서](https://code.claude.com/docs)
[샘플 프로젝트](./00-sample-project.md)
[같은 문서의 표 절로](#7-표)
[다른 문서의 특정 절로](./06-github-version-control.md#2-1-브랜치-전략-github-flow)
<https://github.com>
```

| 종류 | 쓰는 법 | 요령 |
|---|---|---|
| 외부 링크 | `[글자](https://...)` | 링크 글자는 "여기" 대신 **내용**으로 |
| 저장소 안 문서 | `[글자](./경로/파일.md)` | **상대 경로**를 쓴다. 저장소를 옮기거나 포크해도 깨지지 않는다 |
| 문서 안의 절 | `[글자](#제목-앵커)` | 앵커 규칙: 영문은 소문자, 공백은 `-`, 대부분의 문장부호(`.` `,` `:` `(` `)` 등)는 삭제. 한글은 그대로 |
| 주소 그대로 | `<https://...>` | |

> 💡 앵커가 헷갈리면 GitHub에서 제목에 마우스를 올리면 나오는 🔗 아이콘을 눌러 주소를 복사합니다.

### 9-2. 이미지

```markdown
![과정 로드맵](./images/course-roadmap.svg)
```

- `!`가 붙으면 이미지, 대괄호 안은 **대체 텍스트**(이미지를 볼 수 없을 때 읽힘)
- 이미지는 저장소의 `images/` 같은 폴더에 두고 상대 경로로 겁니다
- 크기를 정하려면 HTML을 씁니다: `<img src="./images/a.png" width="400">`

## 10. 인용과 알림 상자

### 10-1. 인용

```markdown
> AI가 코드를 쓰더라도, 시스템의 주인은 개발자다.
```

> AI가 코드를 쓰더라도, 시스템의 주인은 개발자다.

인용은 원래 남의 말을 옮길 때 쓰지만, 실무 문서에서는 **참고·주의 문단**을 눈에 띄게 할 때 많이 씁니다 (이 교육 자료의 `> 💡`, `> ⚠️` 문단).

### 10-2. GitHub 알림 상자

GitHub에서는 인용 첫 줄에 `[!종류]`를 쓰면 색이 있는 상자로 보입니다.

```markdown
> [!NOTE]
> 참고할 내용

> [!TIP]
> 알아 두면 좋은 요령

> [!IMPORTANT]
> 꼭 알아야 할 내용

> [!WARNING]
> 문제가 생길 수 있는 내용

> [!CAUTION]
> 위험한 동작에 대한 경고
```

> [!WARNING]
> 운영 DB 접속 정보는 어떤 문서에도 쓰지 않습니다.

> 💡 GitHub 밖의 도구에서는 평범한 인용으로 보입니다.

## 11. 구분선, 접기, 주석

| 기능 | 원문 | 용도 |
|---|---|---|
| 구분선 | `---` (앞뒤로 빈 줄) | 큰 주제 나누기, 슬라이드 경계 |
| 접기 | `<details><summary>제목</summary> ... </details>` | 퀴즈 정답, 긴 로그, 부가 설명 |
| 주석 | `<!-- 보이지 않는 메모 -->` | 문서에 보이지 않는 메모, 템플릿 안내 |

```markdown
<details>
<summary>정답 보기</summary>

정답은 **에이전트 루프** 덕분입니다.

</details>
```

<details>
<summary>정답 보기</summary>

정답은 **에이전트 루프** 덕분입니다.

</details>

> ⚠️ `<summary>` 다음과 `</details>` 앞에 **빈 줄**을 두어야 안의 마크다운(굵게, 목록)이 제대로 보입니다.
> ⚠️ `---`를 문단 바로 아랫줄에 붙여 쓰면 구분선이 아니라 **제목**(윗줄이 큰 제목)이 됩니다. 앞에 빈 줄을 꼭 둡니다.

## 12. 다이어그램 (Mermaid)

GitHub는 `mermaid` 코드 블록을 그림으로 그려 줍니다. 흐름, 구조, 순서를 글 대신 그림으로 보여 줄 때 씁니다.

````markdown
```mermaid
flowchart LR
    A[요구사항] --> B[계획] --> C[구현] --> D[검토]
```
````

```mermaid
flowchart LR
    A[요구사항] --> B[계획] --> C[구현] --> D[검토]
```

| 자주 쓰는 종류 | 첫 줄 | 용도 |
|---|---|---|
| 흐름도 | `flowchart LR` (가로) / `flowchart TD` (세로) | 절차, 아키텍처 |
| 시퀀스 | `sequenceDiagram` | 요청·응답 순서 |
| ER 다이어그램 | `erDiagram` | 테이블 관계 |
| Git 그래프 | `gitGraph` | 브랜치와 병합 |
| 간트 차트 | `gantt` | 일정 |

> 💡 Mermaid 문법을 외울 필요는 없습니다. **"이 흐름을 mermaid flowchart로 그려줘"**라고 Claude에게 맡기고, 결과를 미리보기로 확인하면 됩니다. 노드 글자에 괄호나 따옴표가 있으면 `["글자(설명)"]`처럼 큰따옴표로 감쌉니다.

## 13. 특수 문자 그대로 쓰기 (이스케이프)

마크다운 문법에 쓰이는 문자를 글자 그대로 보이게 하려면 앞에 `\`를 붙입니다.

| 원문 | 결과 |
|---|---|
| `\*별표\*` | \*별표\* |
| `\# 샵` | \# 샵 |
| `1\. 번호 아님` | 1\. 번호 아님 |
| `a \| b` (표 안) | a \| b |

> 코드(`` ` ``) 안에서는 이스케이프가 필요 없습니다. 특수 문자가 많은 내용은 인라인 코드나 코드 블록으로 쓰는 것이 가장 간단합니다.

## 14. Claude Code와 함께 쓸 때의 작성 요령

### 14-1. CLAUDE.md

```markdown
# EduHub

## 빌드와 테스트
- 백엔드 테스트: `cd backend && ./gradlew test`
- 프론트 개발 서버: `cd frontend && npm run dev`

## 코드 규칙
- Controller → Service → Repository. Controller에서 Repository 직접 호출 금지
- 엔티티를 API 응답으로 반환하지 않는다 (DTO 사용)

## 금지
- `.env`, `application-prod.yml` 수정 금지
```

| 요령 | 이유 |
|---|---|
| **제목으로 주제를 나눈다** | Claude가 "빌드 방법"과 "규칙"을 구분해 찾는다 |
| **한 줄에 규칙 하나, 글머리 목록으로** | 긴 문단보다 놓치지 않는다 |
| **명령·경로·클래스명은 백틱으로** | 정확한 문자열로 인식한다 |
| **짧게 (200줄 이내)** | 매 세션 읽히므로 길면 비용이 늘고 중요한 규칙이 묻힌다 |
| **표는 비교·매핑에만** | "이 패키지는 이 담당" 같은 대응 관계에 좋다 |

### 14-2. 프롬프트도 마크다운으로 구조화하면 좋다

```text
## 목표
과정 목록 API에 분류 필터를 추가한다

## 위치
- @backend/src/main/java/com/example/eduhub/course/CourseController.java

## 완료 기준
- [ ] GET /api/courses?category=JAVA 동작
- [ ] ./gradlew test 통과
```

> 제목·목록·체크리스트로 나누면 Claude가 **목표, 범위, 완료 기준을 빠뜨리지 않고** 처리합니다. 긴 요구사항은 대화창에 붙이지 말고 `docs/*.md` 파일로 저장해 `@`로 참조합니다.

### 14-3. Claude에게 문서 작성을 맡길 때

- "표로 정리해줘", "체크리스트로 만들어줘", "mermaid로 그려줘"처럼 **형식을 지정**하면 원하는 모양으로 나옵니다
- 팀 문서 형식이 있다면 **예시 문서 하나를 `@`로 주고** "이 형식으로"라고 합니다
- 결과는 **미리보기로 확인**합니다. 표 깨짐, 링크 앵커 오류가 가장 흔합니다

## 15. 자주 하는 실수

| 실수 | 증상 | 고치는 법 |
|---|---|---|
| `#제목` (공백 없음) | 제목이 안 되고 글자 그대로 보임 | `# 제목` |
| 표 앞에 빈 줄 없음 | 표가 문단 글자로 보임 | 표 위아래에 빈 줄 |
| 표 구분줄 누락 | 표가 안 됨 | 둘째 줄에 `\|---\|---\|` |
| 표 칸 수가 줄마다 다름 | 칸이 밀리거나 잘림 | 모든 줄의 `\|` 개수를 맞춤 |
| 하위 목록 들여쓰기 부족 | 하위 항목이 같은 단계로 보임 | 2칸(번호 목록 안은 3칸) 들여쓰기 |
| 코드 블록을 닫지 않음 | 문서 끝까지 전부 코드로 보임 | 여는 백틱과 같은 개수로 닫기 |
| `---`를 문단 바로 아래에 | 위 문단이 큰 제목이 됨 | 앞에 빈 줄 |
| 링크에 절대 경로(`/home/...`) | 다른 사람 PC나 GitHub에서 깨짐 | 상대 경로 `./`, `../` |
| 앵커 오타 | 링크를 눌러도 이동하지 않음 | GitHub 제목의 🔗 아이콘으로 복사 |
| 비밀 정보를 문서에 | 저장소 이력에 영원히 남음 | 문서에는 변수 이름만 (`DB_PASSWORD`) |

## 16. 미리보기와 검사 도구

| 도구 | 방법 |
|---|---|
| **VS Code** | 미리보기 `Ctrl+Shift+V`(Mac `Cmd+Shift+V`), 옆에 나란히 `Ctrl+K V`. Mermaid는 확장(예: Markdown Preview Mermaid Support) 설치 |
| **IntelliJ IDEA** | `.md` 파일을 열면 편집기와 미리보기가 나란히 보임 (내장 Markdown 플러그인) |
| **GitHub** | 파일 편집 화면의 **Preview** 탭, PR·이슈 작성 화면의 **Preview** 탭 |
| **markdownlint** | 문법 규칙 검사 (VS Code 확장, CLI `markdownlint-cli2`). 들여쓰기·빈 줄·제목 단계 실수를 잡아 준다 |
| **Prettier** | 표 칸 너비와 목록 기호를 자동 정리 |

> 💡 문서 검사를 훅으로 자동화할 수도 있습니다. 예: `.md` 파일을 수정하면 markdownlint를 실행하는 PostToolUse 훅 ([설정·훅 예제](./03-settings-skills-agents-hooks.md)).
